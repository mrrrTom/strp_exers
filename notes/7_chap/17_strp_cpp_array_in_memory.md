    Массив можно расположить в разных "хранилищах". Рассмотрим такой пример[1]:
    
    ```cpp
    int arr1[1] = { 7 }; // в статическом хранилище

    int main()
    {
    	int arr2[1] = { 8 }; // в стеке
    	int* arr3 = new int[1] { 9 }; // в куче
    	return 0;
    }
    ```
    
    Попробуем выяснить, где в реальности будут находиться созданные объекты.
    Для этого скомпилируем наш код с помощью команды: 
    ```bash
    g++ -g main.cpp
    ```

    Полученный исполняемы файл запустим в gdb:
    ```bash
    gdb ./a.out
    ```
    
    С помощью соответствующих команд выясним адреса хранения данных:
    ```
    p &arr1[2,3]
    ```

    Я получил следующие значения:
    arr1 - 0x40400c
    arr2 - 0x7fffffffddf4
    arr3 - 0x7fffffffddf8

    Чтобы понять, что это за области памяти, в которых расположены наши
    переменные, нужно, например, найти мапинг памяти для этого процесса.
    Если нам известен идентификатор процесса (например, нашли в ps -a), то 
    на Linux это можно сделать с помощью файла maps в папке, соответствующей
    найденному PID процесса.
    Для моего процесса вот некоторые строчки из файла:
    
    00404000-00405000 rw-p 00003000 00:28 760191     /home/tom/source/cpp1/a.out
    00405000-00426000 rw-p 00000000 00:00 0                               [heap]
    7ffffffde000-7ffffffff000 rw-p 00000000 00:00 0                      [stack]
    
    Из представленного видно, что arr2 находится в стеке, как и arr3, a arr1
    находится в какой-то неопределённой области. Нахождение arr2 в стеке
    ожидаемо, а почему там оказалась arr3? А она то и не там, дело в том, что
    при запросе ```p &arr3``` я узнал адрес хранения указателя, так как у
    переменной arr3 тип - указатель на int. Указатель, естественно, хранится в
    стеке. Если же запросим значение arr3, то получим - 0x4172b0, что ожидаемо
    говорит о нахождении объекта в куче.
    Чтобы понять, где же оказался объект arr1 с помощью команды
    ```objdump -h a.out``` найдём расположение интересующих нас секций и их
    размер:
    
    ```
    .data         00000008  0000000000404008  0000000000404008  00003008  2**2
                  CONTENTS, ALLOC, LOAD, DATA
    .bss          00000008  0000000000404010  0000000000404010  00003010  2**0
                  ALLOC
    ```
    Таким образом arr1 попал в секцию .data. Эта секция соответсвует
    инициализированным данным для программы (так как он объявлен на уровне
    'программы', то там и находится физически объект). Получается, что все по
    местам)
